## web

### 垂直越权

之前在moectf做过类似的题，所以这题进去看到身份是guest、目标写着"拿到internal权限"的时候，我第一反应就是按F12。

在Application里翻cookie，发现role居然可以直接编辑，当时还挺高兴，觉得改个internal就完事了。

改成internal和admin，刷新，没用。

然后就卡住了，回去翻源码，在注释里看到一句：个性化预览通过查询参数指定账号：/?name=<账号>，下面还贴心地写了内测演示账号lain。

这不明摆着让我去试吗。在搜索框里输lain（URL里其实就是/?name=lain），页面直接403，提示所需权限为knight。

行吧，回去把key-cookie改成knight，再刷新。

这次终于不是403了，换成"客户端不受支持，必须要用期望客户端"。

到这里我才反应过来，这题是一层一层来的：先泄露入口，再泄露权限名，最后连客户端都要对。在"更多网络条件"里把默认代理关掉，填上它要的期望代理，刷新，flag出来了。

复盘：cookie、User-Agent、代理这些客户端能随便改的东西，只能当线索，永远不能当权限判断的依据。另外报错信息真的要看，它每报一次错，基本就把下一步的方向告诉你了。

### 目录扫描

这题页面很简单，一个输入框，两个按钮，一个请求批准，一个检查。

先看前端js：两个接口都是POST，body就是textarea里的原始字符串，没有解析成对象再stringify，Checkout还用X-Approval这个请求头传审批值。也就是说，重复的JSON键会原样送到后端。

题干都提示扫目录了，那就扫吧。没有目录扫描工具，常见路径手敲一遍：/src、/source、/app.py、/server.py、/debug、/backup、/robots.txt。

在/src拿到了源码，里面有两处flag，可惜都不是真的。

真正关键的是这两个解析函数：

```python
def audit_pairs(pairs):
    result = {}
    for key, value in pairs:
        if key not in result:     # 重复键保留第一个
            result[key] = value
    return result

def audit_decode(raw):
    value = json.loads(raw.decode("utf-8"), object_pairs_hook=audit_pairs)

def checkout_decode(raw):
    value = json.loads(raw.decode("utf-8"))   # 重复键保留最后一个
```

审批用audit_decode（第一个赢），结算用checkout_decode（最后一个赢），同一段文字念出两个意思。

所以payload就很自然了：合法值写前面给它审，目标值写后面给它结。

```json
{"account":"guest","product":"sticker","role":"customer","quantity":1,"role":"admin","product":"flag"}
```

最后那个判断是order.get("product")=="flag" and order.get("role")=="admin"，直接命中。

复盘：以前只知道JSON重复键，没想到不同解析器保留的值不一样；另外前端不解析、原样转发，本身就是个信号。

### 命令行注入

这题一进去，页面基本是个音乐播放器，题干里倒是夹带了不少私货（少量题目夹杂大量私货这一块）。

查源码，发现居然还留了sourcemap，顺着sourcemap把前端源码还原出来，关键接口有两个：

- POST /api/window：管会话状态，设置窗口开没开
- POST /api/ensemble：提交乐谱，parts里可以放乐器

先按{"title":"...","parts":{...}}的结构试，返回了个我不认识的单词，查了一下是notation，记谱法。

乐谱里描述一个音，最常见的就是"音名+八度"，比如C4。改成C4，这次通了。

然后是rain，源码里的隐藏第五元素，提示只有开窗才能进去。

先{"state":"open"}开窗，再带上rain，开始注入。

;被拦了，fuzz一圈发现\n能用，那就好办了。

后面就比较机械了，pwd、ls /、ls /app、env，一步步看，最后在环境变量里翻到了flag。

复盘：sourcemap上线一定要删；状态类和注入类接口经常是连在一起的；黑名单永远写不全，分隔符被拦就换一个，\n、|、&、&&都值得试。

## misc

### 被揉坏的芙芙

这是我在？ctf做的第一个misc，看样子出题人和我都是个芙厨，题目"芙芙图片被挤坏了"。

用imhex打开，IHDR里宽就剩144了，高是1524，CRC全是00 00 00 00。

宽被改坏了，那就要算回来：PNG解压后的总字节数 = 高 × (1 + 宽 × 每像素字节数)，这题颜色类型6（RGBA）、位深8，所以每像素4字节。

再结合题干给的那串神秘字符（现在知道那是正确的CRC），反推宽是2560，也就是0x0A00。

把IHDR的宽改成00 00 0A 00，CRC算一下，跟题干给的完全一致，保存，flag出来了。

复盘：PNG的文件头、CRC32、IDAT解压后的长度，这几个东西是连在一起的，改结构之前先把数算清楚。另外flag是"crc32 is important"，也算官方提示了。

结果是芙莉莲吗出题人你这家伙，我还以为是芙宁娜呢

### 伪加密

这题我一开始的表现非常丢人：看见"需要密码"，直接hashcat上字典，133MB的字典跑完不够又换更大的，跑半天啥也没有。

（前面已经忏悔过一次了，这里再忏悔一次。）

后来才去看十六进制：ZIP的通用标志位在PK+6的位置，本来00 00表示没加密，题里被改成了奇数。

伪加密就一句话：真正的数据没加密，只把标志位改成"已加密"来吓你。

这题改了四处，全部09 08改成08 08，就能打开了。

打开以后里面还有个真的加了密的zip，这回才是要爆破的：zip2john出hash，hashcat用掩码qctf2026?1?1?1?1，字符集?l?d_，密码qctf2026g0od。

复盘：先看结构再上工具，伪加密和真加密长得一样，但处理方式完全不同。

### 中国人能飞

这题算是misc的综合拼盘：

- part1：伪加密
- part2：摩斯密码
- part3：MP3的ID3v2.3标签

前两个不说了，第三个有意思：ID3v2.3是写在MP3文件头部的，不是文件末尾，结构大概是"10字节标签头 + 一堆帧 + 填充"，每个帧有4字节的帧ID，TIT2是歌名、TPE1是歌手、APIC是封面、COMM是备注。

所以音频题不能只听，还得会看元数据。

### ezFilter

题目有1024个文件，真正的flag只在其中一个里面，探测的时候返回hot、warm、cold三种状态。

我第一反应是二分，试了两次就发现不对劲：二分每次只能砍一半，而且hot和warm都算"在附近"，二分对这种三态反馈很尴尬。

后来查资料才知道有三分搜索这回事。

关键是查询区间要能同时装下hot和warm两组。比如区间长度341，按三分切下来是hot 171、warm 170、cold 170，那查询区间就得取hot + warm，正好341这么长。

然后就是反复念经：返回hot直接三分，返回cold就换剩下那组，返回warm就二分。

最后锁到390、391、392，390和391都是cold，那答案就是392。

中间还会随机触发challenge：从十个单词里抽五个做SHA-256，让你找能对上target的组合。这个只能写脚本，再-H把选中的五个词塞进请求头。

坑：脚本没保存cookie，一直403，-c和-b这俩参数真得养成肌肉记忆。

复盘：这题跟web没啥关系，但脚本能力、会话保持、对"返回状态"的建模，都是通用的。web手除了web啥都会。

### LSB

PNG题，先看文件结构，头和尾都正常，像个平平无奇的图片。

上Stegsolve，LSB分析啥也没有，怪了。

后来发现alpha通道是恒定的，勾着α0反而看不到东西，关掉之后隐写内容就出来了。

是一串base64（末尾还有=），解开是一串01，看着像二进制，其实间隔很刻意，那就是摩斯。

对照表翻完，M0RS3_4FT3R_B64_1N_LSB。

复盘：LSB改的是最低位，肉眼看不出差别；做隐写题的时候通道要一个个试，别默认所有通道都有信息。



### git历史操作

题名叫"版本控制很好用"，flag被拆成了两半，工作区里只有半截。

一开始我还以为是reflog或者commit历史，翻了一圈发现答案在stash里：git stash把"做了一半的工作"收起来了，而stash是独立于分支的一套提交。

git stash list、git show、git fsck --lost-found，把那些"不该看到"的blob翻出来，完整flag就在里面。

复盘：工作区、commit、stash、悬空对象，是四套不同的东西。做git题别只会在当前分支上git log。

### 区块链入门

题给了合约源码，说Hello的暗号就写在源码里，看见password就应激这一块。

先eth_call预演，确认返回没问题，再真正上链。

但节点不会帮你签名，所以一笔交易要自己拼：keccak256算函数选择器 → ABI编码参数 → RLP编码 → ECDSA签名 → 拼raw tx → 发POST。

做出来的那一刻还是挺有成就感的，毕竟之前对"上链"的理解就是点个按钮。

复盘：以太坊这套东西，理解了"私钥签名、节点只负责广播"之后就没那么玄了。keccak256 + RLP + 一次HTTP POST，这就是上链。

## 复盘：

1. 也是把看见加密就爆破的毛病改了，现在会先看文件结构、看源码了，?ctf这几道题里，真正需要爆破的其实只有一道。

2. 客户端不可信。cookie、UA、代理、前端校验，都不是真正的安全，真正的判断必须在服务端。

3. 解析器不一致就是漏洞。同一段JSON，一个保留第一个键，一个保留最后一个，这就是漏洞

4. 信息泄露，注释里的?name=lain、没删的sourcemap、能直接访问的/src、ID3标签、stash

5. 工具要练成肌肉记忆。curl的-c/-b、imhex、stegsolve、zip2john、hashcat、git，用得多了就不用现查。
